# Quote generated YAML scalars a parser could read as something else

## Context and Problem Statement

`domainbook new domain 9` wrote `id: 9` into the page's frontmatter. `9` is a
legal slug — lowercase letters and digits joined by single hyphens says nothing
about starting with a letter — but unquoted in YAML it is the integer nine, so
the domain schema saw a number where it wanted text and the next command failed.
The generator wrote a book that did not validate, which is the one thing the
generators are supposed to make impossible.

The same trap sits under `id: no`, `id: y`, `id: off`, `id: true`, `id: null`,
and any id that begins with a digit. All of them are legal ids and all of them
are ambiguous once written into YAML with nothing around them.

## Decision Drivers

- The generators write only what validates. A generated page that `validate`
  then rejects is a broken promise, not an inconvenience.
- Only two values ever reach frontmatter from a generator: an id that has already
  been checked as a slug, and the title-cased form of that same id. The value
  space is small and known, so a fixed list can be complete for it rather than
  approximately right.
- A book is read by tools that are not ours — an editor's YAML mode, a CI script
  in Python, whatever the site build ends up using. It is not enough for the
  bytes to survive our own loader.
- YAML 1.1 and YAML 1.2 disagree about which bare words are booleans. Our loader
  is `yaml` in 1.2 mode, where `y`, `no`, `on` and `off` stay strings; PyYAML and
  a good deal of tooling still read 1.1, where `no` is `false`.

## Considered Options

- Quote every generated scalar, always.
- Quote nothing, and narrow the slug grammar so an ambiguous id cannot exist.
- Quote the scalars a YAML parser could read as something other than text.

## Decision Outcome

Chosen option: "Quote the scalars a YAML parser could read as something other
than text". A generated value is wrapped in double quotes when it starts with a
digit, `-`, `+` or `.`, or when it matches one of `true false null ~ y n yes no
on off`, case-insensitively. Everything else is written bare, so the ordinary
page — `id: ticketing`, `name: Ticketing` — reads as it always did.

The list includes the YAML 1.1 boolean words even though our own loader keeps
them as strings and nothing we ship needs them quoted. That is the judgment in
this decision: correctness is measured against the parsers a book will meet, not
against ours. `id: no` that means the string "no" here and `false` in someone's
Python script is exactly the kind of quiet disagreement a documentation format
cannot afford.

Narrowing the slug grammar was the tempting alternative — no ambiguity if `9` is
not an id — but it makes a rule about the format to work around a rule about
generated bytes, and it would refuse ids that are perfectly reasonable names.
Quoting everything was rejected for the opposite reason: it makes every page
noisier to pay for the handful that need it.

### Consequences

- Good, because `new domain 9`, `new domain no` and their kind now write pages
  that validate, and the generator flow keeps its guarantee end to end.
- Good, because a generated book carries the same data through any YAML parser,
  1.1 or 1.2, rather than only through ours.
- Good, because the rule is a short list in one file, so what counts as ambiguous
  is a question with a place to look rather than a habit spread across the
  generators.
- Bad, because quotes turn up where a person writing by hand would not have put
  them, and `id: "no"` looks like someone was being careful about nothing. Anyone
  reading a generated page has to know why.
- Bad, because the list is a description of what parsers do, not something
  derived from a spec, so it is complete for slug-shaped values and would not be
  for free prose. Nothing today puts free prose in generated frontmatter — a
  decision's title goes in the H1 — and the day something does, this list is not
  enough on its own.
- Neutral, because a book written by hand can still leave the quotes off. That
  book is rejected, and the message says `must be text — put the value in
  quotes`, so the rule is enforced from both ends rather than only generated
  into place.

### Confirmation

The CLI tests run `new domain` with an ambiguous id and then `validate` over the
result, so the generator and the checker have to agree about it rather than each
being tested against its own idea of the file.
