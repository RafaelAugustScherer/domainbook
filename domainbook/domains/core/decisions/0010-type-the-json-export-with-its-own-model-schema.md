# Type the JSON export with its own model schema

## Context and Problem Statement

`export json` writes the whole book as one document, and the roadmap asks for it to
be "JSON-Schema-typed." The schemas the book already generates describe a single
artifact's frontmatter each — a feature's, a decision's — not an assembled book. A
feature's frontmatter names its terms and decisions as bare strings; a reader of
the export should be able to follow one to the entry it points at, in the same
document. So the export needs a schema the frontmatter schemas do not provide: one
for the assembled model, carrying the fields read from a body — a feature's story
and rules — and the references resolved to something a reader can look up.

## Considered Options

- Author a `model` zod schema composing the frontmatter schemas and the
  body-derived fields, generate its JSON Schema and commit it like the others.
- Emit the JSON untyped, and leave a consumer to validate each artifact against
  its own frontmatter schema piecemeal.
- Reuse the per-artifact frontmatter schemas as the export shape, with neither the
  body nor the resolved references.

## Decision Outcome

Chosen option: a `model` schema of its own. `packages/core/src/schemas/model.ts`
composes the existing frontmatter schemas — reusing their fields rather than
restating them — and adds what the export carries beyond frontmatter: a glossary
term's `slug`, a decision's and a debt record's `ref`, `number` and `title`, a
feature's `story` and `rules`. It is generated from zod and committed at
`packages/core/schema/model.schema.json` the way every schema is (`format/ADR-0001`),
so the same drift check guards it. Each decision and debt entry carries the `ref` a
feature's `decisions:` list would name — `ADR-NNNN` at the book level,
`<domain>/ADR-NNNN` in a domain — so a reference resolves to an entry present in
the document rather than pointing outside it.

### Consequences

- Good, because `book.json` is one typed document a tool reads without parsing
  markdown, and every reference in it resolves within it.
- Good, because the schema is generated and drift-checked like the rest, so it
  cannot fall out of step with the zod it comes from.
- Bad, because the model restates the shape of the artifacts a second time, as an
  aggregate: a field added to an artifact is added to its frontmatter schema and
  reached by the model that composes it. Composing by shape keeps them from
  drifting in silence, but the aggregate is still a second surface to hold in view.
- Bad, because a reference is resolved by leaving the id in place and guaranteeing
  the entry exists, not by inlining it, so a consumer still does the lookup.

### Confirmation

The `export json` test emits the fixture book and parses the result against
`modelSchema`, and asserts a feature's `decisions:` references resolve to entries
present in the document. The committed `model.schema.json` is regenerated by the
schema drift check, so it stays the JSON Schema form of the zod it is built from.
